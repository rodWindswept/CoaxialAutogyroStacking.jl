## 2. CODE BUGS & ISSUES (new findings from deep read)

### 2a. `rotor_disk_area` ignores `hub_radius` — dead field
**File:** `src/rotor.jl:53-55`  
**Severity:** Medium

```julia
function rotor_disk_area(rotor::AutogyroRotor)
    return π * rotor.radius^2  # should be π*(R² − r_hub²)
end
```

`hub_radius` exists on the struct but is never subtracted. A 3m rotor with 0.1m hub → 0.1% error (negligible). But the field exists, suggesting it should matter. Either use it or remove it.

### 2b. `compute_figures_of_merit` hardcodes rotor_mass=5.0 kg
**File:** `src/sweep.jl:212`  
**Severity:** Medium

```julia
mass_total = g.n_rotors[1] * 5.0  # hardcoded!
```

`parameter_sweep()` accepts `rotor_mass` as a keyword argument (default 5.0), but `compute_figures_of_merit()` hardcodes 5.0. If someone runs a sweep with `rotor_mass=8.0`, the N/kg figures of merit are wrong. This is a **data corruption bug** — silently wrong results.

### 2c. `parameter_sweep` never varies `blade_pitch_deg`
**File:** `src/sweep.jl:143`  
**Severity:** Low (v1 scope)

The sweep creates all rotors with `blade_pitch_deg = 0.0` (hardcoded). The field exists but cannot be swept. This is consistent with v1 scope but the sweep config doesn't expose it, even though the struct supports it. Add to v2 scope explicitly.

### 2d. `lift_force_steady` — `F_hub` definition inconsistent with anchor tension
**File:** `src/optimisation.jl:113-123`  
**Severity:** Medium (conceptual)

`F_hub` = sum of raw `F_line` from all rotors (no weight subtraction, no line drag).  
`T_anchor` = tension at bottom of stack (includes weight subtraction + line drag + rope-can't-push clamping).

These are different quantities. The KTD.jl integration pattern expects `F_hub` to be the force available at the attachment point — which should match `T_anchor`. Currently they diverge whenever rotor weight is non-zero. A single rotor at 50° elevation: F_hub ≈ 327 N, T_anchor ≈ 297 N (weight subtracted). Which is the "hub force"?

### 2e. No test for intermediate-rotor-slack edge case
**File:** `src/stack.jl:83-108`  
**Severity:** Low-Med

`stack_tension_profile` has `max(0, profile[k-1] + delta)` for rope-can't-push. Tested for zero wind (all slack). NOT tested for: one rotor producing less than its weight while others produce lift. E.g., rotor 2 at tilt=-40° produces F_line=0 while rotors 1 and 3 pull hard. What happens at rotor 2's position? The `max(0,...)` clamp should handle it, but it's untested.

### 2f. `optimal_pitch` docstring says "blade pitch" but code sweeps tilt
**File:** `src/optimisation.jl:3-7`  
**Severity:** High (user-facing lie)

```
Grid-search the blade pitch (−30° to 30° in 0.5° steps)
```

Actually searches `tilt_deg`. For a user who reads the docs and trusts the API, this is a trap. Rename to `optimal_tilt` or fix to sweep the correct field.

### 2g. `AutogyroStack` struct stores single `line_angle_deg` — blocks v2 polygon geometry
**File:** `src/stack.jl:35-45`  
**Severity:** Architecture

v2 requires per-segment line angles (polygon chain). The current struct has one global angle. This means v2 requires a struct redesign, not just new functions. The `section_lengths` vector already exists — add a parallel `section_angles` vector now, even if it's filled with the same value in v1. This makes v2 a function change, not a struct change.

### 2h. `bare_line_drag` signature doesn't take line angle
**File:** `src/line_section.jl:26-31`  
**Severity:** Architecture

The function takes `(rho, v_wind, diameter, length)` but should take `(rho, v_wind, diameter, length, line_angle_deg)` for crossflow correction. Changing the signature now would require updating all call sites. This is a standard API evolution — do it before v1.0 locks the interface.

## 3. PHYSICS MODEL GAPS (beyond literature audit)

### 3a. No autorotation RPM model
**Severity: CRITICAL for any rotational analysis**

The PCA-2 data is for a rotor at its natural autorotation equilibrium RPM. We get forces but never compute RPM. Without RPM:
- Can't compute centrifugal blade loads (structural sizing)
- Can't compute bearing speed limits (bearing selection)
- Can't compute gyroscopic precession moments (bearing loads during line angle changes)
- Can't verify the Reynolds number regime matches PCA-2 test conditions
- Can't compute tip speed (noise constraint)

The entire mechanical design (Phase 9) is dimensioning a system whose rotational speed is unknown.

### 3b. No gyroscopic precession loads
**Severity: HIGH for bearing design**

A spinning rotor disk on a flexible Dyneema line is a gyroscope. When the line angle changes (gust, launch, landing), gyroscopic precession creates out-of-plane bearing loads. At 3m radius, autorotating at ~200 RPM (guess), the angular momentum could be substantial. The dual-molding thrust bearing sees pure thrust in steady state — but dynamic precession loads could be the sizing case.

### 3c. No wind shear / velocity gradient
**Severity: Medium**

Wind speed increases with altitude (log law / power law). A 90m tall stack (4 rotors × 30m spacing) has meaningful velocity difference top-to-bottom. Top rotors see higher v_wind → produce more lift → tension profile is non-uniform in a way the model can't capture. This couples with the polygon line geometry problem — higher wind at top means more drag at top, shaping the line differently.

### 3d. No blade structural feasibility check
**Severity: MEDIUM for Phase 9**

The sweep finds R=3m optimal with 5kg mass budget. Is a 3m-radius, 2-blade autogyro rotor physically possible at 5kg per rotor? PCA-2 had a 13.7m rotor diameter with 3 blades — not directly comparable. A 6m diameter rotor with 2 blades at autorotation RPM experiences centrifugal stress. The mass budget needs verification against structural requirements.

### 3e. No autorotation startup / lock-in analysis
**Severity: Low-Med**

Autogyro rotors need to spin up from rest to autorotation RPM. This requires a certain minimum wind speed and favorable blade pitch. The model assumes the rotor is always at equilibrium RPM. At launch (low wind, low altitude), will the rotors actually start? This is a real operational constraint.

### 3f. PCA-2 data applicability: 1930s autogyro vs. modern kite rotor
**Severity: HIGH**

The PCA-2 was a 1930s autogyro aircraft with:
- 3 articulated blades with flapping hinges
- High solidity (σ estimated ~0.08-0.12)
- Operated at advance ratios μ ~0.2-0.35 (forward flight)
- Had a tailplane, fuselage, and engine

Our system:
- 2 rigid blades, no flapping hinges
- Unknown solidity (0.15m chord at 3m radius → σ = 0.032 — **3× lower than PCA-2**)
- Operates at μ ≈ 0 (pure axial flow for a kite on a line)
- No fuselage, empennage below rotor

CL/CD at a given α depends on solidity, blade twist, airfoil, and advance ratio. The Duquette & Visser (2003) data shows σ=0.05 vs σ=0.25 changes torque by 900%. We're using PCA-2 CL/CD (σ≈0.10) for a rotor with σ=0.032. The error could be factor-of-2 or more.

### 3g. Tip-speed Mach number / noise
**Severity: Medium (buyer/viability)**

The user's memory says: "noise (tip speed, altitude, line vortex shedding), social acceptability, siting. A turbine that sounds like a helicopter won't sell." Without RPM, we can't compute tip speed. A 3m rotor at 300 RPM has tip speed ≈ 94 m/s — approaching Mach 0.28, which is audible. The KTD.jl architectural decision sets tip speed ≤ 120 m/s for noise. We need to check this for the autogyro rotors.

## 4. MECHANICAL DESIGN GAPS (Phase 9 territory)

### 4a. Bearing thrust load not quantified
**Severity: HIGH for Phase 9a**

At R=3m, CL=0.95, 8 m/s: F_lift ≈ 1,050 N per rotor. This thrust goes through the dual-molding sandwich bearings. What size bearings? Off-the-shelf thrust bearings (e.g., SKF 51100 series) have dynamic load ratings of 5-50 kN. At 1 kN steady + dynamic precession, we might be fine — but we don't know because we haven't calculated.

### 4b. Dyneema-through-bearing wear
**Severity: Medium**

The Dyneema line passes through the hollow hub and tube bore. If the hub rotates around the line (it does — the hub autorotates relative to the line), there's relative motion between line and hub bore. Dyneema has poor abrasion resistance. A bearing or bushing is needed between the line and the rotating hub. Not shown in schematics.

### 4c. Swashplate pushrod loads unknown
**Severity: Medium for Phase 9d**

Blade pitching moment depends on blade chord, span, airfoil, and operating condition. None of this is modelled (PCA-2 is a disk model). Can't size actuators without knowing the load. This makes Phase 9d (actuator selection) speculative without BEM.

### 4d. Empennage sizing needs inflow velocity
**Severity: Medium for Phase 9b**

H-stab area for pitch trim depends on dynamic pressure at the tail. The tail is in the rotor's induced flow field (autogyro inflow from below). The inflow velocity is modified by the rotor (induction). Without an induction model, empennage sizing is a guess.

### 4e. Thermal expansion mismatch in webbing capture
**Severity: Low**

Dyneema CTE: negative (−12×10⁻⁶ /K). Aluminium CTE: +23×10⁻⁶ /K. Carbon fibre CTE: near zero. At altitude (−20°C vs +20°C ground), a 1m aluminium tube shrinks ~0.9mm relative to Dyneema. The webbing capture must accommodate this or risk loosening. Not a showstopper, but a real detail.

### 4f. No aeroelastic stability check
**Severity: MEDIUM**

Rotating blades on a flexible line with bearings and a tail — this system has multiple aeroelastic modes:
- Blade flutter (classical bending-torsion coupling from propeller theory)
- Disk whirl (rotor disk precession coupled with line flexibility)
- Empennage flutter (tail boom on a flexible mount)

None of these are analysed. At 3m radius and high RPM, flutter is a real risk. Even if v1 scope excludes dynamics, the mechanical design needs to be flutter-free by construction.

## 5. PROJECT ARCHITECTURE & PROCESS ISSUES

### 5a. Phase 9 depends on physics not yet modelled
**Severity: HIGH**

Phase 9 tasks (dimensioning assembly, sizing empennage, selecting actuators, BOM) all depend on quantities the v1 model doesn't compute:
- **RPM** → needed for bearing speed rating, centrifugal stress, tip speed
- **Blade pitching moment** → needed for actuator sizing  
- **Inflow field** → needed for empennage sizing
- **Gyroscopic loads** → needed for bearing sizing

Phase 9 is trying to do mechanical design with an aerodynamic model that doesn't provide the inputs the mechanical design needs. The dependency chain is: BEM (v2) → RPM, pitching moment → mechanical sizing. Without BEM, Phase 9 is dimensioning from guesses.

### 5b. Mass budget self-inconsistency
**Severity: MEDIUM**

The sweep assumes 5 kg/rotor regardless of radius. A 3m radius rotor (with 2 blades, hub, bearings, swashplate, empennage) almost certainly weighs more than a 0.5m rotor. If mass scales with R² or R³, the Pareto front shifts — larger rotors become less attractive. The sweep's best configuration (R=3m, N=4) may not survive a mass-consistent reanalysis.

### 5c. The literature audit is 24 days stale with zero fixes
**Severity: PROCESS**

8 of 11 findings from June 8 are still open. The two critical items (PCA-2 geometry independence, PCA-2 axes convention) remain unaddressed. This blocks confidence in any results derived from the model.

### 5d. `PHASE9_PLAN.md` says "R=3.0m (best config from Phase 8 sweep)" as anchor for dimensioning
**Severity: HIGH**

The sweep found R=3m optimal under v1 assumptions (5kg mass, no induction, straight line, PCA-2 for all geometries). Using this as the mechanical design anchor without addressing the assumptions is premature. If mass scaling or induction reduces the optimal radius to 2m, the entire Phase 9 dimensioning is off.

### 5e. No uncertainty quantification anywhere
**Severity: MEDIUM**

The sweep produces deterministic outputs with no error bars. Given the assumptions (wrong solidity, no induction, unverified axes convention, fixed mass), the actual anchor tension could be off by factor-of-2 or more. The project needs an uncertainty budget before committing to mechanical dimensions.

### 5f. `Project.toml` has heavy deps for what the core does
**Severity: Low**

Bonito, GLMakie, WGLMakie, CairoMakie, Pluto are all dashboard/notebook deps. The core physics package (PCA-2, rotor, stack, optimisation) needs only `DataFrames` and `Statistics`. Consider splitting into `CoaxialAutogyroStacking.jl` (core) and `CoaxialAutogyroStackingDashboards.jl` (viz) so the core is lightweight for KTD.jl integration.
